# Step 3.7 Flash 最佳实践

steppi 针对 Step 3.7 Flash 做了多层优化，但模型本身的特性决定了它不适合照搬大模型的使用方式。本页讲清楚为什么要这么设计，以及你在日常使用中怎么配合。

## 为什么 Flash 需要特别对待

Step 3.7 Flash 是稀疏 MoE 架构（198B 总参数 / 11B 激活参数），推理成本低、速度快，但在以下场景会明显掉点：

- **上下文过长**：system prompt + 工具结果 + 历史消息超过一定长度后，指令遵循质量会下降
- **工具契约含糊**：verbose 或边界不清的工具描述会让小模型猜错用法
- **单条工具结果过大**：一条 5000 行的 bash 输出会直接淹没后续指令
- **压缩太懒**：等到上下文几乎满了才压缩，模型已经“忘了”最初的指令

steppi 的设计哲学不是“让 Flash 表现得像 700B 模型”，而是“别在无关紧要的东西上浪费它的上下文”。

## steppi 做了什么

### 1. 精简 system prompt

把 system prompt 从 ~3500 字符压缩到 ~2000 字符，只保留：

- 身份与工作环境
- 核心行为准则
- 工具使用纪律
- 上下文预算意识

删除的包括：冗余的自我描述、模型训练截止日期提醒（改用实时搜索）、可做可不做的工具建议。

### 2. 收紧工具结果上限

工具结果兜底上限从 400K 字符降到 200K 字符，与 `web_fetch` 的单条上限对齐。对小模型尤其重要：更短的上下文意味着更稳定的指令遵循。

### 3. 提前触发压缩

默认压缩触发比例从 85% 降到 75%，压缩时只保留最近 4 条消息（原 6 条），用户原话保真预算从 20K token 降到 10K token。压缩更早、更激进，防止上下文被工具结果撑爆。

### 4. 语义化工具结果预处理

对 `bash` 和 `read_file` 的超长结果做结构保留截断：

- `bash`：保留头 50 行 + 尾 20 行，中间省略
- `read_file`：保留头 10 段 + 尾 5 段，中间省略

这样模型既能拿到关键上下文，又不会被冗余输出淹没。

### 5. 精修核心工具描述

`bash`、`spawn_agent`、`edit_file`、`ask_user`、`skill` 五个核心工具的 description 重写，让 Flash 一次就能理解“什么时候该用、该怎么用”。

## 你怎么配合

### 任务描述尽量具体

小模型的“猜意图”能力不如大模型。与其说“帮我看看这个项目”，不如说：

> 读取 `src/agent/loop.ts`，找出 `maybeCompact` 函数，解释它为什么在 micro 之后还要按比例折算 usedTokens。

### 复杂任务拆成步骤

Flash 更适合“单轮明确指令”，而不是“开放式探索”。如果任务涉及多个文件或多个阶段，考虑：

1. 先用 `spawn_agent` 做只读调查
2.  yourself 综合结论
3.  再动手修改

### 控制工具输出范围

- `bash` 尽量加 `head`/`tail`/`grep` 缩小输出
- `read_file` 用 `offset`/`limit` 读段落，不要一次读 10000 行
- `glob`/`grep` 加具体路径和文件名模式，不要搜整个 `src/`

### 善用 `/compact`

如果感觉模型开始“忘事”或重复输出，手动触发 `/compact` 压缩上下文。越早压缩，损失越小。

###  thinking 档位选择

- **低难度任务**（单文件修改、简单问答）：用 `low` 或 `off`，省钱省时
- **中等难度**（多文件改动、需要推理）：用 `medium`
- **高难度**（复杂架构设计、多步调试）：用 `high`

Flash 的 `high` 档思考量远低于大模型的 `high`，不要期待它能“想很久”。

## 已知限制

- **工具调用格式错误**：Flash 偶尔会生成不合法的 tool call（缺字段、类型错）。当前代码会直接拒绝，未来可能加入更宽容的修正重试
- **长推理链不稳定**：超过 10 轮以上的复杂任务，Flash 的指令遵循会明显下降，建议拆分成多个子任务
- **上下文窗口**：虽然支持 256K，但实际稳定工作区间在 100K 以内，超过后质量下降明显

## 设计决策

以下决策记录了 steppi 针对 Step 3.7 Flash 做优化时的关键 trade-off，方便后续维护者理解“为什么这么做”而不是“做了什么”。

### System prompt 为什么砍到 ~2000 字符

小模型的注意力窗口有限，system prompt 里的每一条指令都在和用户消息、工具结果竞争位置。我们把 prompt 从 ~3500 字符砍到 ~2000，删除的是：

- 冗余的自我描述（“我是 Step Code，一个运行在终端上的 TUI Agent”）
- 模型训练截止日期提醒（改用实时搜索）
- 可做可不做的工具建议（“需要为文档找配图时，用 web_image_search”）

保留的是：身份、工作环境、核心行为准则、工具使用纪律、上下文预算意识。

**没有删除的**：权限系统、计划模式、子 agent 委派纪律——这些是安全边界，不随模型大小改变。

### 工具结果上限为什么从 400K 降到 200K

2026-08-02 的两次 OOM 事故证明工具结果全仓没有任何长度上限会有问题。但 400K 的上限对大模型来说问题不大，对 Flash 来说已经能造成明显的指令遵循下降。

200K 与 `web_fetch` 的单条上限对齐，形成统一的心智模型：“任何单次工具结果超过 200K 都会被截断”。

### 压缩策略为什么更激进

默认触发比例从 85% 降到 75%，保留消息从 6 条降到 4 条，用户原话预算从 20K 降到 10K。

原因：Flash 的上下文质量下降曲线比大模型更陡。等到 85% 才压缩时，模型已经“忘了”很多早期指令。75% 触发 + 更激进的保留策略，是在“压缩质量”和“上下文新鲜度”之间给 Flash 的平衡点。

### 工具调用容错为什么只做轻度修正

当前实现只处理两种最常见的小模型格式错误：
- 字符串 `"true"/"false"` → 布尔值
- 数值字符串 → 数字

没有做更激进的容错（比如缺字段时猜默认值、类型错时强行转换），原因是：
1. 小模型的格式错误通常是“类型层面”的，不是“语义层面”的
2. 语义层面的猜测（比如缺 `path` 时 guess 用户想读什么文件）风险太高，可能造成副作用
3. 轻度修正已经能覆盖 80% 的常见错误，投入更高风险的行为不划算
