## 0. 结论先行（最重要的一段）

**本仓库不是「Agent 原型」——它已经是 v0.1.12 的成熟项目。** 任务书假设的「两天从原型建起」与事实不符，因此本轮工作的性质必须重新定义：

> **不是新建，而是收敛（convergence）。**
> 核心 harness 已存在且可用；真正缺的是「对外可讲清楚」「首次用户能自己跑通」「发布卫生」。

三条硬约束必须遵守（任务书 §30）：不虚构 benchmark、不虚构 token、不虚构模型能力；不为了 TUI 推翻已有 Agent 核心；不删已有可用功能。

**最大的真实差距是叙事与文档，不是代码。** README 只有 85 行、缺架构图与真实 Demo；`architecture.md` / `harness.md` / `benchmark.md` / `troubleshooting.md` 四份文档完全缺失。而这恰恰是「发社区」的门面。

## 3. 哪些能力已经可复用（不要重造）

- **`wire.jsonl` 事件流** —— 已是结构化事实源，trace 与 benchmark 都该复用它，不要再发明一套。
- **benchmark harness**（runner / dashboard / analysis）—— 已能跑 5 个 fixture，是「harness 效果」叙事的现成证据生产器。
- **Mission 的 verifier**（`src/agent/mission/verify.ts`）—— 独立判定 + harness/断言分流 + 证据包，是 §16 Verification 的现成底座。
- **pi-tui 前端** —— 已是产品的门面且可用，不要为「更好看」替换。

## 4. 当前最明显的架构问题

1. **叙事与代码脱节**：README 把项目讲成「Step 3.7 Flash 稳定性优化」，而真正的差异化（harness 工程 + 可观测 + 恢复）散落在代码与 `docs/` 深处，外人看不见。
2. **`src/tools/` 36 个文件平铺**，无分组；工具面偏大（已用 `toolSearch` 与 experimental gate 缓解，但目录组织未跟上）。
3. **口径镜像债务**：`postGreen.ts` 与 `benchmark/analysis/validationMetrics.ts` 各自实现了一套 vitest 识别/计数规则，文件注释已自陈「两处需人工同步」——真实漂移风险。
4. **文档双份维护**：14 页 × zh/en = 28 个文件，改一处必须同步另一处，漂移风险高。
5. **验证未进入默认体验**：`postGreenTermination` 默认关闭，模型说「done」时默认不强制跑测试——与 §16「不允许仅凭模型说 Done」有距离。
6. **工作区卫生**：7 个 `bench-setup-*` + 3 个 `test-bash-*` 残留目录、`nul`、`picker-debug.log`、`test-output.log`、根目录一次性调试脚本。

## 9. 诚实性约束（贯穿全程，不可妥协）

1. **历史 benchmark 结果不可引用**：`benchmark/results/` 下 128 份结果混着 D1 修复前的框架缺陷（误删测试文件导致 verify 恒失败），**不是模型能力**。Demo 与文档中的任何数字都必须来自本轮**重新实跑**。
2. **不虚构 token / 延迟**：只写 provider 可靠返回的字段；拿不到就写「未采集」，不估算充数。
3. **Demo 必须真实**：`step-3.7-flash` 凭据可用（`~/.step-pilot/config.toml`），具备实跑条件；若某次实跑失败，就如实记录失败与恢复，不做「理想化」剪辑。
4. **不夸大**：不宣称「修复了 N 个上游 bug」、不公布覆盖率百分比、不做成本/省钱叙事。
